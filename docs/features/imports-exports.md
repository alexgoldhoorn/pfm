# Broker parsers, PDT format, import/export and bookings

> Moved out of `CLAUDE.md` on 2026-09-25 so it isn't loaded into every session. CLAUDE.md keeps the must-know gotchas and links here; this file is the full reference. "See the X section" means the matching file in `docs/features/`, or CLAUDE.md.

### CSV / File Parsers
Each broker has a standalone parser returning `LLMTransaction` objects via `ParseResult`. Valid `tx_type`: `buy`, `sell`, `dividend`, `interest`. `LLMTransaction` (in `portf_manager/llm_types.py`) has an optional `asset_type: str = ""` field — when set, `imports.py` uses it instead of defaulting to `"stock"` on save.
- `indexacapital_csv_parser.py` — semicolon CSV, European numbers, ISINs. `Tipo` values matched by **prefix**: any `SUSCRIPCIÓN*` (including `SUSCRIPCIÓN POR TRASPASO`, an internal fund-switch) → buy, any `REEMBOLSO*` (including `REEMBOLSO POR TRASPASO`) → sell — do not require an exact string match, IndexaCapital's export uses several suffixed variants. Header row explicitly skipped. Also auto-detects "Movimientos" cash statement → SEPA → deposit/withdrawal bookings; fund subscriptions skipped. Every row is typed `mutual_fund` (Indexa holds index mutual funds, never ETFs; it was `etf` until 2026-09-26). The type matters: fund overlaps are only `transferable` (traspaso) between mutual funds.
- `myinvestor_csv_parser.py` — "Movimientos Mi Cuenta": INVEST/`MY INVESTOR`/`Sent from <service>`=deposit (`MY INVESTOR` is MyInvestor's own in-app P2P/instant-transfer feature name, not personal data, so it's a safe fixed keyword; `Sent from Revolut` etc. generalizes on the phrasing, not the service name); `NAME @ QTY` with Importe<0=buy, >0=dividend; positive no-`@`=dividend lump-sum. No ISIN/fees → buys flagged "review". Platform fees (`SUSCRIPCIÓN PREMIUM`, comisión, ...) → withdrawal booking. `Transferencia ...` (e.g. `Transferencia desde MyInvestor`, money sent out) → deposit/withdrawal booking by the amount's sign; before 2026-10-28 these were skipped, so cash sent out never reached the ledger. `ANUL[.] NAME [@ QTY]` (negative, Fecha de valor = the reversed payout) → a `dividend` with a **negative** amount on NAME, never a buy. `AHORRO`, `INVEST <n>` and `SALEPROCEEDS` (a sale at another broker paid in) are deposits. MyInvestor truncates names at ~30 chars, which can cut off a trade's `@ qty` (`... ACC @`, or `... ETF @ 30` for 300 units), so a positive row is **skipped as a probable sale**, never a dividend, when the name ends in a bare `@`, when it has no `@` and is ≥ 100 €, or when it pays ≥ 15 € a unit (dividends on these statements run cents to a few euros a share). Truncated ETF names often don't resolve to the stored asset (`get_asset_by_name` matches the exact name, then the name without legal-form suffixes such as NV/SA/PLC/Inc, see below, but never a truncated prefix), so a re-import of an old statement can add its dividends a second time on a new fake asset — check new-asset rows in the preview. Remunerated-cash interest (`Liq./Liquidación intereses <mes>`, `PERIODO dd/mm/yyyy dd/mm/yyyy`, `regularización intereses <mes>`) → `interest` transaction against a synthetic `MYINVESTOR-CASH` asset (`asset_type="cash"`); its IRPF withholding (`Ret./Retención IRPF intereses <mes>`, or the "Ret. liq intereses ... promo" variant) is always a *separate* CSV line at the same date as its credit — the parser buffers withholding rows first, then folds a same-date match into the credit row's `tax` field (two passes, since file order between the pair isn't reliable); an unmatched withholding row still becomes its own (negative) interest row so cash isn't silently dropped. `regularización` same-day +/- pairs share identical concept text on both sides, so unlike the credit/withholding pair they're **not** folded — each imported standalone. **Known unfixable gap**: a P2P transfer labelled with an arbitrary person's name has the exact same shape as a genuine lump-sum dividend (positive, no `@`, no fixed keyword — e.g. a real "EXAMPLE PHARMA LABORATORIES" dividend looks identical text-pattern-wise) — no generalizable way to tell them apart without either false-positiving real dividends or hardcoding a specific name into a public parser, so these still land as a dividend on a fake symbol and need catching by eye in the import preview. Deposit-maturity lines (`APERTURA DEP.`/`INTERESES DEP.`) aren't recognized at all — MyInvestor's own fixed-term deposit product is handled instead through the `fixed_deposits` table (see below); importing this CSV blindly would double-count a matured deposit as a bogus dividend on top of that.
- `myinvestor_paste_parser.py` — MyInvestor statements pasted as text.
- `mintos_csv_parser.py` — P2P statement (tens of thousands of micro-rows; a real one is ~35-40k). Aggregates interest/withholding **per month** into `interest` transactions vs synthetic `MINTOS` asset (`asset_type='bond'`, `auto_price=0`, price pinned at **1.0** — 1 unit = €1 of principal outstanding, since P2P loans have no market price and Mintos itself values them at par). P2P principal moving in/out (`Inversión`, `Capital recibido`, buyback-guarantee repayments, secondary-market trades) is likewise summed **separately per month, buy vs sell, not netted** into MINTOS buy/sell transactions at price=1.0 — same treatment as ordinary buy/sell, so cost basis stays exactly aligned with quantity. Mintos's separate **Bonds sleeve** ("Transferencia a/desde inversiones en bonos") carries a real ISIN in `Detalles` and is tracked as genuine buy/interest transactions against that ISIN (also priced at par — no realistic Yahoo ticker for these). The asset is auto-named `f"Mintos Bond {isin}"` (`portf_server/routers/imports.py`) since Mintos's own export has no bond name/ticker alongside the ISIN — cosmetic only, worth renaming to the bond's real name (e.g. via the Assets page or `PUT /api/v1/assets/{id}`) for readability, but **this name does not affect PDT import matching** — PDT resolves the security by the exported ISIN regardless of what name string accompanies it (verified: renaming had zero effect on PDT's import status for two real Mintos bonds). A first-time bond ISIN will still show as "Suggestie" in PDT's import review even when it resolves to the exact right catalog entry — that's PDT's normal "not yet in your account, confirm to add" step (see `inPortfolio` in `pdt-search-symbols`/`pdt-get-symbol`), not an export defect, and isn't something to chase away. The **ETF sleeve** ("Pago de la cartera ETF saliente") carries *no* per-fund ISIN anywhere in this export — it's recorded as a plain withdrawal booking; attributing it to specific ETF ISINs isn't something a stateless parser can do and needs a one-off manual per-ISIN buy import from whatever source does carry that detail (e.g. a PDT XLSX export) — **don't also leave the matching withdrawal booking in place once that's done, or the same funding gets subtracted from cash twice** (found and fixed 2026-08-18: two `Pago de la cartera ETF saliente` withdrawals duplicated buy transactions for the same money that had been imported separately). Deposits/fees kept individual → bookings. Large files → nginx `client_max_body_size 25m`.
- `coinbase_csv_parser.py` — Fiat Deposit/Withdrawal rows → bookings; staking income → `interest` tx (qty=1, price=EUR total). `parse_coinbase_csv` returns a `CoinbaseParseResult(importable, skipped, bookings)`; the router's `_parse_coinbase` turns it into `(previews, bookings, skipped)`.
- `generic_csv_parser.py` — Universal broker-agnostic CSV. Required cols: `date`, `symbol`, `type`, `quantity`, `price`, `currency`. Optional: `name`, `fees`, `asset_type`, `notes`. Case-insensitive multilingual headers (EN/ES/NL); type synonyms for buy/sell/dividend/interest; auto-detects delimiter, date style (EU/US), and decimal style (EU/US — `_detect_decimal_style` scans first 10 rows for unambiguous cells with both `,` and `.`); `asset_type` column mapped via `_ASSET_TYPE_MAP` → propagated to `LLMTransaction.asset_type` → imports.py uses it instead of defaulting to `"stock"`. The template is not a file in the repo: `downloadGenericTemplate()` (`pfm_core.js`) builds it client-side and downloads it as `generic_import_template.csv`.
- `pdt_xlsx_parser.py` / `pdt_sheets_sync.py` — PDT XLSX and Google Sheets import/export.
- `bookings_csv_parser.py` — generic cash deposit/withdrawal CSV (broker `bookings`): cols `date, action, amount` + optional `currency` (default EUR), `broker`; EN/ES/NL header synonyms, delimiter and decimal style auto-detected. Returns bookings + skipped rows with reasons.
- `deposits_csv_parser.py` — generic fixed-deposit CSV (broker `deposits`) → `PreviewDeposit` rows for the `fixed_deposits` table: `name, principal, interest_rate, start_date, maturity_date` + optional `currency`, `portfolio`, `notes`; same synonym/auto-detect approach.
- `generic_bank_csv_parser.py` / `aeb43_parser.py` — bank statements (CSV, or AEB43/Norma 43 fixed-width, auto-detected with `looks_like_aeb43`) for Spending Tracking via `POST /api/v1/spending/upload`, not `/import/upload`. See `spending.md`.

### PDT Format (`pdt_xlsx_parser.py` and `pdt_sheets_sync.py`)
5 sheets with 3-row header block (machine keys / group labels / display labels), data from row 4: Transactions, Dividends, Bookings, Expenses, Settings.

`PDTXLSXParser.parse(path) → PDTParseResult` | `PDTXLSXExporter.export(db, path)` — writes all 5 sheets.
`PDTSheetsSync(sheet_id).pull() → PDTParseResult` | `PDTSheetsSync(sheet_id).push(db)` — reads/writes Google Sheet.

Google Sheets API: `UNFORMATTED_VALUE + SERIAL_NUMBER` for reading (dates = floats → `_serial_to_date`); `USER_ENTERED` for writing. Auth: `GOOGLE_SERVICE_ACCOUNT_FILE=service-account.json`.

**PDT compatibility rules** (verified against live PDT API):
- Effect types: exactly `"Stock market"`, `"Crypto"`, `"Commodity"` (case-sensitive)
- Crypto/commodity assets: **must have empty exchange** — use `_pdt_exchange(exchange, asset_type)` helper
- `mutual_fund` assets: **exchange must be the literal string `"Funds"`**, not blank and not a real exchange name (`_pdt_exchange` forces this regardless of any stored `assets.exchange`) — per PDT's own Google Sheets import docs (help.portfoliodividendtracker.com/article/126): "wanneer de transactie gaat om een fund type, selecteer dan de beurs 'Funds'". Without it, PDT's import can't tell to search its fund catalog and the row lands in the import review as an unresolved "Suggestie" even though the ISIN itself is valid and already in PDT's catalog. `bond` assets get the literal exchange `"Bonds"` the same way (also forced by `_pdt_exchange`). It isn't in PDT's help article, but it's in the template's `Exchanges` tab and it's the exchange PDT's own import review suggests for a bond; exported empty, every bond landed in the review as "selecteer of controleer de beurs" (2026-11-18). The effect type stays `"Stock market"` (PDT has no bond effect type).
- A heuristic broker import (e.g. MyInvestor CSV, which has no fund/ETF/bond signal in its own export) can land a genuine OEIC/mutual-fund share class as `asset_type='stock'` by default — check `GET /api/v1/assets/{id}` for held funds and correct via `PUT /api/v1/assets/{id} {"asset_type":"mutual_fund"}` if so, otherwise the `"Funds"` exchange rule above silently never applies to it.
- **`bond` transactions must be rescaled to PDT's percent-of-par convention before export**, via `_pdt_bond_quantity_price(asset_type, quantity, price)` (`pdt_xlsx_parser.py`, used by both the XLSX writer and the Sheets push): `quantity → quantity/100`, `price → price*100`. pfm stores bond positions par-priced (1 unit = 1 currency unit of principal, price pinned at 1.0 — see the Mintos parser notes above), but PDT prices a real market-traded bond it recognizes in its own catalog as percent-of-par against a 100-nominal lot. Exporting our raw par-convention numbers unscaled made PDT compute `quantity * live_price` directly and wildly overstate the position — confirmed against a real Mintos Bonds-sleeve holding, which PDT valued at exactly `quantity * price` (no /100) instead of `(quantity/100) * price` — a phantom gain of some thousands of percent in PDT's UI. Total invested (`quantity * price`) is unchanged by the rescale, so cost-basis import is correct either way — only PDT's own live-priced valuation was wrong before this fix. This is separate from, and unrelated to, the "Funds" exchange rule above — a genuine numeric export bug, not a PDT-side "Suggestie" cosmetic issue.
- Bookings display label (row 2 col 0): `" "` (single space, not `"Broker"`)
- Canonical exchange names: `"XETRA Exchange"`, `"Nasdaq"`, `"MyInvestor"`, `"Indexa Capital"`
- **Broker = portfolio name, checked by PDT against a fixed list.** PDT's import validates the Broker column against the template's `Brokers` tab (~170 names; no custom brokers, PDT's API has the same list). A portfolio named after a broker PDT doesn't list fails every row with "Geselecteerde Broker is ongeldig" / "Selected broker is invalid". The `pdt_broker_map` app setting (`portf_manager/parsers/pdt_brokers.py`, JSON `{"<pfm portfolio>": "<PDT broker>"}`) renames such a portfolio on every export (Sheets push and XLSX) and maps it back on every PDT import (Sheets pull, PDT XLSX `/upload`, case-insensitive), so pfm keeps its own name and a round trip doesn't create a second portfolio. Read/set it with `GET`/`PUT /api/v1/sync/pdt-config` (`broker_map`; omitted fields are unchanged, `{}` clears). The Sheets push reads the `Brokers` tab after building the rows and returns `warnings` for any exported broker not in it (the tab is a formula that fetches PDT's list; with fewer than 20 names it is still loading, and the push returns one "not checked" note instead of flagging every broker) (shown in the web push result and the CLI); the XLSX export has no list to check against. Two portfolios mapped to the same PDT broker merge on pull (first map entry wins).
- Dividend action always `"Cash"` (Cash/Stock/Staking subtype not stored separately)
- Only parse 3 sheets on import (Transactions/Dividends/Bookings); write all 5 on export/push.
- **Synthetic assets are not exported** (`_PDT_SKIP_SYMBOLS` / `_pdt_exports_asset`, both exporters): the Mintos P2P pool (`MINTOS`) stands for no real security, so PDT's import stopped on every row as "Onbekend effect". Its buys/sells are left out; the Mintos bookings still export, so in PDT that money shows as cash. Interest rows never go to PDT anyway. The real Mintos bonds (ISIN assets) still export.
- A price or amount of 0 is a value, not a missing field: both PDT readers (XLSX and Sheets) check those with `is None`. The Sheets reader used truthiness until 2026-11-18 and skipped a 0-price dust sale.

### Import API (`portf_server/routers/imports.py`)
- `POST /api/v1/import/upload` — multipart file + `broker` field → parse preview (no DB write)
- `POST /api/v1/import/save` — `SaveRequest(transactions, bookings, portfolio_id, duplicate_action)` → write to DB
- `POST /api/v1/import/check-duplicates` — flag duplicates (no write); powers text/LLM preview
- `POST /api/v1/import/import-file` — multipart `file`, `portfolio_id`, optional `format`: parse, de-duplicate and save a broker file in one call (the broker counterpart of `/spending/import-file`; for unattended callers). The portfolio must be `account_type='brokerage'` (else 400). Deterministic parsers only, never the LLM. Formats (`FILE_IMPORT_FORMATS`): `indexacapital`, `myinvestor`, `coinbase`, `mintos`, `generic` (not `pdt`: a PDT export spans several brokers, and this endpoint saves everything into one portfolio, so an xlsx or `format=pdt` is a 400 pointing at the web Import page or the PDT sync); `format` wins, else the **file** decides (Coinbase's `Transaction Type`+`Timestamp` header; Mintos `Tipo de pago`+`Volumen de negocios`; MyInvestor `Fecha de operación;…;Concepto;Importe`; Indexa `Código ISIN`+`Participaciones` or the `Movimiento`+`Saldo` cash statement; a generic CSV whose header resolves date/symbol/type/quantity/price/currency), and only a header that matches nothing falls back to the portfolio's name or entity (`indexa`, `myinvestor`, `coinbase`, `mintos`). No match is a 400 naming what was looked for. It shares `_parse_broker_file` with `/upload` and `_save_import` with `/save` (never a copy) and uses the web default: rows flagged duplicate and rows a parser marks `skip` (MyInvestor buy/sell) are left out, duplicate action `skip`. Every row is checked against and saved into the chosen portfolio (the parser's broker tag is ignored). A booking flagged only as a **near** match (same amount, other date) is **not** saved (an unattended import must not double-count a deposit; the web preview leaves it unticked too) and is counted in `bookings_to_review`, with a warning to import it from the web Import page if it is real; exact booking duplicates stay in `duplicates_skipped`. Response, counts and dates only: `{portfolio_id, portfolio_name, format, parsed, imported, duplicates_skipped, bookings_to_review, bookings_imported, new_assets (a count), first_date, last_date, warnings}`. **All or nothing**: `_save_import(..., journal=_ImportJournal())` records every transaction, booking and new asset it creates and every `asset_type` it corrects; the first failing row deletes the transactions and bookings, restores the old types and hard-deletes the new assets, then the call is a 500 (`Import aborted, nothing was stored…`). A bad file or portfolio is a 400. A module lock serialises calls (a plain `def` endpoint); `/import/save` takes the same lock, so a person and the job never save at once (the lock sits in the endpoints, not in `_save_import`, so there is no re-entry). Every failure after the first write, including the booking duplicate check, rolls back when a journal is passed. `settle_after_bookings` runs once after the rows; if it fails the rows stay and the response warns. Not covered by the rollback: the settle step itself (it runs after everything else succeeded) and anything another request outside the import endpoints writes meanwhile.
- Brokers (`SUPPORTED_BROKERS`): `indexacapital`, `myinvestor`, `myinvestor_paste` (pasted statement text, `myinvestor_paste_parser.py`), `mintos`, `coinbase`, `pdt`, `bookings`, `deposits`, `generic`
- `duplicate_action`: `skip` (default) | `add` | `overwrite`. `force=True` is legacy alias for `add`. **It applies to transactions only.** A duplicate booking is skipped unless that row carries `PreviewBooking.force=true`, which the preview sets when you tick a flagged cash row by hand. Before this, choosing "Import anyway" to re-add one transaction also copied every duplicate booking in the file (how a 200 € deposit got in twice on 2026-08-18).
- `find_duplicate_transaction` is **time-aware**: matches date + time-of-day only when both rows carry one. Price match is `ABS((price - incoming) / NULLIF(price, 0)) < 0.00001` — the whole ratio must be inside `ABS()`, not just the numerator; wrapping only `(price - incoming)` (a bug present until this was caught while importing negative-amount `interest` rows) makes the ratio's sign flip whenever the *existing* row's price is negative, so it's always `< 0.00001` and every same-asset/type/date row false-positives as a duplicate regardless of the actual price difference. A stored price of 0 (crypto dust sales) has no ratio, so it matches only an incoming price of exactly 0 (`OR (price = 0 AND ? = 0)`); with `NULLIF` alone such a row was never a duplicate and every re-pull added it again. Dividends and interest match on their cash amount (`quantity × price`, ±0.005) instead of quantity and price separately, since the MyInvestor paste stores a dividend as 1 × amount and the CSV as shares × per-share amount.

### Duplicate rules (all import paths)
`/import/save`, `/import/upload` + `/check-duplicates` previews, the PDT Sheets pull (`POST /sync/pdt-pull`) and the CLI PDT XLSX import all use the same rules. The pull and the CLI used to check nothing, so re-running one doubled everything.
- A row is compared only with rows stored **before** this import, never with rows of the same import. Two identical trades or deposits in one file are both kept. Transactions do this through `import_dedup.TransactionDeduplicator`, which passes `exclude_ids` to `find_duplicate_transaction`.
- Each stored row matches at most one incoming row.
- **Bookings** go through `Database.match_existing_bookings(rows, window_days=3)`, which matches the whole import at once. A booking with the same action, amount (±0.005), currency, portfolio and date is an exact match. One up to 3 days away is a near match, but **only if its date lies within the import's date span for that portfolio**. Two sources can date one transfer a day apart (MyInvestor operation vs value date: #101 on 04/03 and #102 on 03/03 were the same 1.000 €). An import that covers the stored date and has no row on it describes the same transfer. A stored booking outside the span belongs to a period the import doesn't cover, so a same-amount row near it is a new deposit (regular DCA transfers every 2–3 days). A one-row paste therefore catches only exact dates. The preview shows why a row was flagged in `duplicate_reason`, as the badge tooltip. `find_duplicate_booking` (exact only) remains for single-row callers.
- `/save` requires a non-blank `date` per transaction (rejected per-row into `errors`, same as any other save failure) — a preview row's date can be blank pending manual fill-in, but it must not reach the DB blank.
- `/save` also **corrects `asset_type` on an already-existing asset** when the incoming transaction carries a different, non-empty, valid type (e.g. an asset first created `stock` by a heuristic-based import, later re-imported from a parser — like IndexaCapital — that explicitly tags it `mutual_fund`). This means a parser's hardcoded type overwrites a hand-corrected one on every re-import, so the parser's type must be right. Only ever updates `asset_type`; never touches other asset fields.

- `GET /api/v1/export/pdt` — PDT XLSX (5 sheets)

- Platform logic in `portf_manager/platform_export.py`.

### Bookings API
`GET|POST /api/v1/bookings/`, `DELETE /api/v1/bookings/{id}`. Importable via PDT (sheet/XLSX), generic `bookings` CSV, LLM extraction (`POST /api/v1/llm/extract-bookings`), or manual form — the manual form exists in two places sharing the same `POST` call: the Import/Export page's Bookings tab (`#addBookingForm`) and an "Add Cash" button on the Transactions page (`#addCashModal`/`#addCashForm`, `setupAddCash()` in `pfm_features.js`).

### Asset lookup by name (imports without an ISIN)
- `db.get_asset_by_name(name)` (import preview and save, after the symbol lookup): exact case-insensitive name first (ISIN-keyed record preferred); else `normalize_asset_name` on both sides (casefold, dots dropped so `N.V.` = `NV`, other punctuation to spaces, trailing legal-form words NV/SA/PLC/AG/SE/Inc/Corp/Ltd/SpA/ASA/Oyj/AB/KGaA/BV/LLC/Co removed). One match wins, or the one ISIN-keyed record among several; anything else ambiguous is no match, so a new asset is created as before. Share-class words (ACC, DIST, ETF) are kept: they name different securities. Truncated prefixes are deliberately not matched (an ACC name cut short also prefixes its DIST class). Added 2026-11-18 after a MyInvestor dividend for "… NV" landed on a new fake asset beside the stored ISIN asset.

### Preview duplicate detection needs `broker`
- **File-import preview duplicate detection requires `PreviewTransaction.broker`**: `POST /api/v1/import/upload` has no `portfolio_id` param — `_flag_duplicates()` (imports.py) only knows which portfolio to check against via each row's `broker` field (`db.get_portfolio_by_name(tx.broker)`), same field the `/save` step uses as its portfolio fallback. A parser that omits `broker=` gets `portfolio_id=None` passed into `find_duplicate_transaction`'s `(portfolio_id IS ? OR portfolio_id = ?)` filter, which then only matches other NULL-portfolio rows — since real imported transactions always have a real portfolio_id, **every** row looks new and duplicate detection silently does nothing. Coinbase and IndexaCapital both set `broker=` for this reason; a new broker parser must too.
