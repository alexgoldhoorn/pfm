# Action Items

> Moved out of `CLAUDE.md` on 2026-09-25 so it isn't loaded into every session. CLAUDE.md keeps the must-know gotchas and links here; this file is the full reference. "See the X section" means the matching file in `docs/features/`, or CLAUDE.md.

### Action Items API (`portf_server/routers/action_items.py` + `services/action_items.py`)
- `GET /api/v1/action-items/` — plain `def`; aggregates independent checks (each wrapped in try/except so one failure doesn't take down the rest), sorted by severity: stale broker imports (`import`, 60+ days no transaction/booking/spending activity — see below), data-quality summary (`data_quality`, reuses `dq_duplicates`/`dq_suspicious` in-process and **counts only findings nobody has checked or snoozed** — ack id `dq:{finding_key}`, so `context` carries `count`, `checked`, `tab: "dq"` and the open `finding_ids`, the title reads "N … to review" and the item disappears once every finding is checked; **not** `dq_reconciliation`, which has no automatic pass/fail threshold, only informational implied-cash figures for manual comparison), price-update-run failures (`errors`, latest run's `error_count`/`error_symbols`), stale research on held positions (`errors`, no `research_notes` row in 90+ days — detects staleness, not past LLM-call failures, since only successful saves are persisted), off-track and overdue goals (`goals`, reuses `services/goals.py` `list_goals_with_progress`: an unmet goal whose date has passed is titled "is overdue" and names the date, the rest "is off track" with the required and planned monthly amounts; retirement-named goals are skipped), watchlist/price-target alerts (`watchlist`, reuses `check_watchlist_alerts` and the extracted `compute_price_target_alerts`), budget overruns (`budget`, reuses `GET /api/v1/budgets/summary` in-process — see the Budgeting section), fund look-through gaps (`exposure`, `check_fund_exposure` — see below), recurring charges (`spending`, `check_recurring_charges` — see below), plus the held-price, balance-sheet, retirement and allocation checks described below. The registered checks are the module-level `_CHECKS` tuple in `services/action_items.py` (`checks_for_tests()` exposes it, so a test can assert a check is wired in). `GET /?status=open|all` (default `open`) returns `{"items": [...], "summary": {...}, "acks": {...}, "generated_at": "..."}` via `action_items_report()`; each item is `{id, category, severity, title, detail, link_page, context, status, ack}` (`status` is `open`/`checked`/`snoozed`, `ack` the stored record or null). `summary` counts every item whatever the filter (`total`, `open`, `checked`, `snoozed`, `open_by_severity`, `open_by_category`); `acks` is the whole stored map so the web client can apply it to the Net Worth items it computes itself. Diagnostics-linked items (price-update failures, held prices, data quality) carry `context.tab` (`price`/`dq`) so "Go to page" opens the right Diagnostics tab (`data-diag-tab` → `localStorage.pfmDiagTab`).
- **`check_held_prices`** (`errors` category, `medium`) raises one item per price the spike guard is holding back (`price_guard.list_held_prices`): id `errors:price-held:{asset_id}:{date}`, title "Price for {name} held: {pct} % in {days} day(s)", detail naming both prices and the two ways out (tomorrow's fetch confirms it if it repeats, or store a manual price), links to Diagnostics. See `prices-market.md`.
- **`check_fund_exposure`** (`exposure` category, `portf_manager/services/action_items.py`) calls `exposure.compute_exposure()` directly (same module the diversification/fund-overlap endpoints use) and turns its `coverage`/overlap output into items: `medium` for each `coverage.unprofiled` fund (no look-through profile — sector/region/currency all understate it), `low` for each `coverage.stale_profiles` fund (profile `as_of` over a year old), and `low` for each `consolidation_candidate` overlap group (two-plus held funds tracking the same index). **This last check is `if group["kind"] != "consolidation_candidate": continue` in `check_fund_exposure` — only `consolidation_candidate` groups raise an item.** Both other `find_fund_overlaps` kinds are deliberately excluded: `informational`/nested (a narrower fund inside a broader one is a legitimate tilt) and `similar` (the no-benchmark cosine-similarity fallback — alike weights aren't the same index, so it's shown on the Analytics page but never raised as a nudge). All flagged items link to the Analytics page, where clicking through opens the `#fpModal` profile editor for the named fund(s).
- **Net Worth gaps are deliberately NOT included server-side** — the frontend Action Items page fetches `GET /api/v1/networth/` + `/networth/cashflow` and runs the existing client-only `computeNetWorthChecklist()` against them, merging the result in via `mergeActionItems()` (`pfm_features.js`). Avoids maintaining the same checklist rules in two languages.
- Web: new "Action Items" nav page (top-level, next to Dashboard). Follow-up state (checked / snoozed) is **server-side** since 2026-10-24 — see *Follow-up state* below; the pre-existing `localStorage["pfmDismissedActionItems"]` / `pfmDismissedIssues` lists are migrated once by `migrateLocalDismissals()` (`pfm_core.js`, posted as `checked` with a "migrated" note, then removed). Item ids are deterministic per entity (`import:portfolio:{id}`, `dq:duplicates`, `errors:price-update:{run_id}`, `goals:{goal_id}`, `recurring:missed:{portfolio_id}:{merchant}:{next_expected}`, ...) so dismissing one doesn't hide a *new* occurrence (e.g. a later failing price-update run has a different `run_id`).
- Price-target rows (`check_price_alerts`) end their detail with "Since {first_seen}." when the crossing is older than today (state in `app_settings` `price_alert_state`, see `research-rebalance.md`); the check reads without recording.
- `research.py`'s `/alerts/check` endpoint delegates to `compute_price_target_alerts(db)`, a pure function extracted so the Action Items aggregator can reuse the same alert computation without re-triggering `send_alerts_push()` on every page load.
- Item `title`/`detail` show `"Name (SYMBOL)"` rather than a bare symbol/ISIN where a name is available — `_name_code(name, symbol)` helper in `action_items.py`, applied to price-update failures (looks up each failed symbol's asset), stale research, and both watchlist/price-target alert checks (which already carried `name` in their source dicts but weren't using it). `check_data_quality` stays aggregate-only (no per-asset symbol to attach a name to).
- **Stale imports cover bank accounts too, with an explicit "upload from" date.** `db.get_portfolio_date_ranges()` also returns `first/last_spending_date` per portfolio (from `spending_transactions`, `MIN`/`MAX(date) GROUP BY portfolio_id`) alongside the existing transaction/booking columns — bank-type portfolios never populate `transactions`/`bookings`, so without this they were silently never flagged as stale regardless of how long they'd gone unimported. `check_stale_imports`'s `context` carries `portfolio_name`, `account_type` (`brokerage`/`bank`), and `since_date` (last activity + 1 day, ISO); `detail` states it explicitly ("Upload transactions for {name} from {since_date} onward...") instead of a generic "import recent statements" nudge. Web: clicking "Go to page" on one of these stashes that context in `window._pendingImportFocus` (`createNavigationManager`'s click handler, `pfm_features.js`) before navigating; `setupImportExportTabs()` (re-run on every navigation to the Import/Export page) calls `_applyPendingImportFocus()`, which pre-selects `#ioFilePortfolio` (brokerage — also guesses `#ioFileBroker` from the portfolio name via the existing `BROKER_TO_PORTFOLIO` map, same as manually picking a broker) or `#ioSpImportAccountSelect` (bank), and shows a one-shot `#ioPendingImportBanner` restating the account name and since-date. Consumed once then cleared, so a later normal visit to the page shows no banner.
- **`check_balance_sheet_freshness`** (`networth` category, `portf_manager/services/action_items.py`) raises one item per stale balance-sheet line, id `balance_sheet_stale:{line_id}`: severity `low` for `manual` lines and `medium` for every other source (positions, ledger cash, account valuation, bank statement). A bank account with no balance reads "{name} has no balance". The detail is a plain sentence per source from `_stale_line_detail` (what the figure is based on, its date, what to do); the line's own `note` is a short label for the Net Worth page, and internal source names such as `cash_ledger` never reach the item. A manual line whose name matches a portfolio also raises `balance_sheet_duplicate:{line_id}` (`low`). Setup gaps stay client-side in `computeNetWorthChecklist`; this check covers freshness only. See the Balance sheet section of `networth-portfolios.md`.
- **`check_retirement_readiness`** (`retirement` category) raises one item, id `retirement_readiness`, from the base-case verdict of the first scenario: `medium` for `short`, `high` for `at_risk`, `low` for `needs_setup` (no birth date); nothing when on track or when the status is `insufficient_data`. Both new checks link to the Net Worth page (`link_page: networth`).
- **`check_mortgage_payment`** (`networth` category, `medium`, 2026-11-15) raises `mortgage:payment-differs:{loan_id}` per loan whose latest complete month with a bank debit differs from the schedule by more than a euro ("Mortgage payment differs from the schedule: update the rate and balance"; the detail adds the rate-revised hint when two months differ equally). Nothing without a bank category to compare with, and a month the statements do not cover yet is never judged. Links to the Loans & Mortgage page (`link_page: loans`). See `mortgage.md`.
- **`check_wealth_scenario`** (`forecast` category, web label "Wealth Plan") raises one `medium` item, `wealth_scenario:behind:{scenario_id}`, when the **primary** saved Wealth Simulator scenario's tracking status is `behind` (the real change in net worth since the baseline fell below the scenario's confidence band); non-primary scenarios are what-ifs and raise nothing, and `too_early`/`no_baseline` raise nothing. Links to the Wealth Simulator page (`link_page: forecast`). See `wealth-simulator.md`.
- **`check_recurring_charges`** (`spending` category, reuses `services/recurring.load_recurring`) raises `recurring:missed:{portfolio_id}:{merchant}:{next_expected}` (`medium`) for a recurring charge whose due date has passed inside an imported statement — "missed" needs an import past the due date, so a late import never looks like a cancelled subscription — and `recurring:price:{portfolio_id}:{merchant}:{last_date}` (`low`) when an active charge in the last `RECURRING_PRICE_RECENT_DAYS` (45) rose by `RECURRING_PRICE_RISE_PCT` (10 %) or more. Price drops raise nothing. Both link to the Spending page. See `spending.md`.
- **`check_unmatched_pattern_transfers`** (`spending` category, `low`) raises `transfer:unmatched:{spending_id}` for a row with `transfer_source='pattern'`, no link, dated between `TRANSFER_REVIEW_DAYS` (90) and `TRANSFER_SETTLE_DAYS` (3) days ago: newer rows may just be waiting for the other import, older ones are closed-account history (reachable through the "Transfers without counterpart" filter). Rows marked by hand never raise an item.
- **`check_bookings_without_bank_leg`** (`spending` category, `medium`) raises `transfer:no-bank-leg:{booking_id}` for a `Deposit`/`Withdrawal` booking of at least `BOOKING_BANK_LEG_MIN` (100, in its own currency) in the last 90 days that no spending row links to. Conservative test: it fires only if **every** bank account with a row in the last 90 days has a row dated after the booking date plus 3 days (a booking does not say which bank it came from). Both link to the Spending page. See `spending.md`.
- **`check_allocation`** (`allocate` category, `portf_manager/services/action_items.py`) raises up to three items: `allocate:idle_cash` (`low`, buffer above the ceiling, detail gives `idle_eur`), `allocate:buffer_low` (`medium`, buffer below the floor) and `allocate:targets_incomplete` (`low`, the reasons from `allocator.check_targets`; no item when no targets exist at all). Nothing for `insufficient_data`. See `allocator.md`.
- **`check_decision_reviews`** (`decisions` category, 2026-11-01) raises `decision:review:{id}` (`medium`) for every open journal decision whose `review_on` is today or earlier, with the price move since the decision in the detail when both prices are known; `link_page: decisions`. See `decisions.md`.
- **Managed portfolios (2026-11-01):** `check_price_alerts` and `check_stale_research` ignore holdings that exist only in portfolios flagged `is_managed` (robo-advisor), and `check_price_alerts` emits one item per symbol — a watchlist buy-zone hit that also crossed its research target carries the target in its detail instead of a second row. Details in `research-rebalance.md`.

### Follow-up state: checked / snoozed (`services/action_item_acks.py`, 2026-10-24)
- **Why.** Dismissals used to live in each browser's `localStorage`, so the phone and the laptop disagreed, nothing recorded *why* an item was waved away, and the AI chat and MCP tools could not see what had already been looked at. Now one record per finding lives in `app_settings` under `action_item_ack:{id}` (same store the price guard uses — no schema bump): `{"status": "checked"|"snoozed", "note", "at", "until"}`. `checked` hides the finding until its id changes (ids name one concrete occurrence, e.g. a later failing price-update run has a new `run_id`); `snoozed` hides it through `until` (inclusive), after which it reads as `open` again while the note survives. `status: open` deletes the record. The PostgreSQL adapter has no settings methods: `list_acks` returns `{}` there and `set_ack` raises `NotImplementedError` (501 from the API).
- **Ids.** Action items use their own id (`dq:duplicates`, `goals:3`, `networth:bank_balance` …). The per-finding Data Quality rows use `dq:{finding_key}` — `dq:dup:{tx_a}:{tx_b}` and `dq:susp:{tx_id}:{check}` — the same keys `dq_duplicates`/`dq_suspicious` return. `ack_is_active(ack, today)` / `effective_status` are the one rule; `annotate_items` and `summarize_items` build the report.
- **API.** `POST /api/v1/action-items/ack` body `{id, status: open|checked|snoozed, note?, until? (YYYY-MM-DD), days?}` → `{id, status, ack|null}` (422 on a snooze without a date or a date in the past); `GET /api/v1/action-items/acks` → `{acks}`. Both are static routes registered before nothing else conflicts (there is no `/{id}` route in this router).
- **Web.** Action Items page: severity filter buttons, a *Show checked & snoozed* switch, "N open · N checked · N snoozed" summary, and per item **Go to page**, **Ask AI** (opens a chat thread via `openChatWithContext` with `actionItemChatPrompt(item)`), **Checked** (asks for an optional note through `noteDialog`) and a **Snooze 7 / 30 days** menu; a resolved item shows its badge + note and a **Reopen** button. The header's **Ask AI** sends every open item (`actionItemsChatPrompt`). Diagnostics Data Quality cards carry the same buttons per finding (`_dqActionButtons`), deleting a duplicate records a `checked` ack with "Deleted transaction #id" for the audit trail, and the overview chips/tab badges count only open findings. Pure helpers (`ackIsActive`, `activeAckIds`, `findingStatus`, `annotateActionItems`, `filterActionItems`, `actionItemsSummaryText`, `ackLabel`, the three `…ChatPrompt` builders, `diagOverviewModel`, `utcDate`) are `window.`-exported and tested in `web_client/js/tests/action_items_followup.test.mjs`.
- **Dashboard.** `loadDashboardActionItems` asks for `status=open` and hides the client-side Net Worth items with `activeAckIds(acks)`; the detail panel gains an **Ask AI** link and a "N checked or snoozed" note. The per-device "hide until the set changes" dismiss of the dashboard group (`pfmDashActionItemsDismissed`) is unchanged — it is a display preference, not a decision about a finding.
- **Chat.** Three tools in `portf_server/chat_tools.py`: `get_action_items(include_resolved=false)` (items with `status`, `note`, `snoozed_until`, plus `summary`), `set_action_item_status(id, status, note?, days?)` (the only chat tool that writes; it changes nothing but this follow-up state, and the system prompt tells the model to use it only when the user asks to mark/snooze/reopen) and `get_diagnostics()` (freshness + stale list, last five price-update runs with `error_symbols`/`api_errors`, open vs checked DQ counts with `finding_id`s, warnings/errors in the last 24 h from `app_logs`). The chat page's empty state offers "What needs my attention?". See `llm.md`.

### Cost control items (2026-11-15)
- **`check_spending_anomalies`** (`spending` category, `low`) turns the unusual charges of the last 14 days (`ANOMALY_ITEM_DAYS`, newest first; the cap of 8 counts only items nobody has checked or snoozed, which are still returned after them so the `all` view shows them) into items. The item id is the anomaly's own deterministic id (`anomaly:large:<row>`, `anomaly:new_merchant:<row>`, `anomaly:category:<name>:<YYYY-MM>`, `anomaly:duplicate:<row>:<row>`), so the existing checked/snoozed state applies; marking the row(s) one-off makes the item go away for good. Details: `spending.md` → Cost control.
- **On pace to exceed** (`budget` category, `low`, in `check_budget_overruns` via `_budget_pace_items`): `budget:pace:<line_id>:<YYYY-MM>` for a cost line whose month-end projection passes its available amount by both `BUDGET_OVERRUN_EUR` and `BUDGET_OVERRUN_PCT`. A line the overrun check already flags for the month gets no pace item. Nothing is raised for a month with nothing imported (no pace exists), for a `too_early` pace (no projection), or without an active budget. The detail names the data-through date, because the projection is an estimate. Details: `budgeting.md`.

### Uncategorised spending (2026-11-17)
- **`check_uncategorized_spending`** (`spending` category, `low`, id
  `spending:uncategorized:<YYYY-MM>`): raised when the last complete month's uncategorised
  outflows are above 5% of that month's spending or above 500 EUR
  (`spending_uncategorized.SHARE_ALERT_PCT` / `TOTAL_ALERT_EUR`). The id carries the
  month, so checking it for one month does not hide the next; the detail names the biggest groups
  from the queue. A month with no imports, or one the data stops short of, is
  never judged; none complete means no item. Links to the Spending page's To
  classify card. Details: `spending.md` → Cost control 2.

### Month close (2026-11-18)

`check_month_close_ready` (in `_CHECKS`, `services/month_close.py`) raises one low item, `spending:month-close:<YYYY-MM>` ("October is ready to close", category `spending`, `link_page` `budget`), only for the last complete calendar month, only from the 5th of the following month, only while that month's imports step is `ok` (every bank account reaches its last day and rows exist) and the month is not closed. Older months never raise one. Closing the month, or reopening it and the imports no longer reaching, removes it. It carries the `spending` priority weight like the other spending items. See `spending.md` -> Month close.

### Triage: groups, priority, top 5 (2026-11-18, `services/action_item_groups.py`)
- **Pure module, no new checks.** Ids and checks are unchanged. A *family* is picked by id prefix from one table (`FAMILY_PREFIXES`): `price_targets` (`research:*`, `watchlist:*`), `budget_pace` (`budget:pace:*`), `budget_overrun` (`budget:line:*`), `recurring_missed`, `fund_exposure` (`exposure:*`), `stale_imports` (`import:portfolio:*`), `cash_freshness` (`balance_sheet_stale:*`). An item in no family stays alone.
- **Folding.** `fold(items)` replaces 3 or more `open` items of a family with one group: `id` `group:<family>`, `kind: "group"`, `family`, `count`, `children` (the original items, priority order), the highest child severity, a count `title` ("22 price targets crossed"), a one-line `detail` (price targets: BUY/SELL counts and how many are new in the last 7 days; pace: the three largest projected overshoots by label; others: the first titles) and the children's `link_page` (null when they differ). Checked and snoozed items are never folded or counted. The group's `priority` is its severity + category weight + the most urgent child's urgency. The price-target and pace items carry `context.triggers`/`since` and `context.label`/`projected_over_eur` for these summaries.
- **Priority.** `priority(item, today)` = severity (high 300, medium 200, low 100) + a category weight from one table (`CATEGORY_WEIGHT`: tax, data quality, retirement 40 down to watchlist 0, always below the gap between two severities) + urgency (0 to 50, from `context.days_left` or a `due`/`due_date` within 45 days). The year-end tax item carries `days_left` in its context. Ties keep the check order.
- **API.** Every item in `GET /action-items/` now has `priority` and `family` (the family name, or `null` when in none; grouped or not, so a client can filter a family that is below the grouping size). With `grouped=true`, `items` is the folded, priority-sorted list, `top` holds the first 5 open entries and `summary.open_entries` the folded open count; `summary` otherwise still counts single items. `POST /action-items/ack` with `id: "group:<family>"` applies the ack to every currently open child, stores nothing under the group id and returns `{id, status, children: [ids]}` (422 for an unknown family). A child that appears later is open.
