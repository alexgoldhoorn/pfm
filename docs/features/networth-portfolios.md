# Net worth, brokers/portfolios, goals, watchlist and sync

> Moved out of `CLAUDE.md` on 2026-09-25 so it isn't loaded into every session. CLAUDE.md keeps the must-know gotchas and links here; this file is the full reference. "See the X section" means the matching file in `docs/features/`, or CLAUDE.md.

### Net Worth API (`portf_server/routers/networth.py`)
- `GET /api/v1/networth/` — brokerage (live positions) + bank accounts (derived balances, see below) + manual assets/liabilities + **active** fixed deposits (principal only) → `net_worth_eur`. `net_worth_eur(db)` is the shared total-only helper — since schema v35 it is `build_balance_sheet(db)["totals"]["net_worth_eur"]` (see Balance sheet below), and Goals imports it so the two pages can't drift apart.
- **Bank-account balances (db v26):** `net_worth_eur(db)`/`GET /api/v1/networth/` sum bank-type portfolios' balances, each derived via `Database.get_latest_bank_balance(portfolio_id)` (most recent `spending_transactions` row with a non-null `balance`, ties broken by highest id) — mirrors how brokerage value is derived from transactions rather than manually re-entered. An account with no balance-bearing import yet is excluded from the total (not zero) and reported as `bank_accounts: [{portfolio_id, name, balance: null, currency: null, balance_eur: null, as_of: null}, ...]`; `bank_accounts_eur` is the rounded EUR sum. The Net Worth page's setup checklist flags such accounts and separately warns if both a manual cash-category asset and a balance-bearing bank account exist (possible double-counting) — no automatic matching or deletion, prompt only. New "Bank Accounts" card on the Net Worth page (`_renderBankAccounts`) shows each account's balance and as-of date.
- Manual assets: `GET|POST /api/v1/networth/` (item), `PUT|DELETE /api/v1/networth/{id}` — categories include `savings_account`/`current_account`/`cash` (bank balances), `property`/`vehicle`/`pension`/`investment_external`, liabilities `mortgage`/`personal_loan`/`car_loan`/`credit_card`/`other_debt`. Flat user-entered amount, no transaction ledger — home/property value only counts toward net worth if entered here (use a current market estimate, not purchase price). Web UI: click the € amount in the items table to edit in place (`window.editManualAssetAmount`, `apiClient.updateManualAsset` → `PUT`) — meant for balances that change often, e.g. a bank account; `updated_at` (bumped by both create and this edit path) is surfaced under bank/cash-category rows as "Updated N days ago", amber past `NW_STALE_DAYS` (30) via `_updatedLine()`/`_daysSince()`.
- Fixed deposits (`portf_server/routers/deposits.py`, `fixed_deposits` table v19): `status` is `active`/`matured`/`closed`. Only `active` deposits count toward net worth. `POST /{id}/mature` posts an interest transaction to a synthetic `DEPOSITS` asset and flips status — nothing does this automatically; the Setup checklist (below) flags deposits past maturity still `active` with a one-click link to the existing "Mark Deposit as Matured" modal.
- Monthly cash flow (`monthly_cashflow` table v20): `GET|POST /api/v1/networth/cashflow`, `DELETE /cashflow/{id}` — categories `salary`/`other_income`/`mortgage`/`loan`/`rest`. Its `net_monthly_eur` and `by_category.mortgage` are read client-side to *suggest* values (new-goal "Monthly €" autofill; Wealth Simulator's monthly-contribution/mortgage-payment prefill via "Load from Net Worth") — the underlying Goals/Forecast projection math still uses each goal's/simulator's own stored fields, not a live read of cashflow.
- **Setup checklist + wizard** (`web_client/js/pfm_analytics.js`): `computeNetWorthChecklist(items, cashflowItems, deposits, bankAccounts)` — pure function, no new backend surface — flags missing home value (only if a mortgage exists), bank/cash accounts, monthly income, plus **mortgage payment** (only if a mortgage exists), **loan payment** (only if a non-mortgage liability exists) and **other recurring expenses** (always) as three separate cashflow-category checks — replaced a single coarse "monthly expenses" item that was satisfied by any one expense row. Also a separate `attention` list for active-but-overdue deposits, and (db v26) `missingBalanceAccounts` (bank accounts with no imported balance yet) plus a `duplicateWarning` string when both a manual cash-category asset and a balance-bearing bank account exist. Rendered as a card above the manual-assets form; "Run setup wizard" opens a modal (`NW_WIZARD_STEP_DEFS`, one entry per checklist key) that calls the same `createManualAsset`/`createCashflowEntry` endpoints as the inline forms, skipping steps already satisfied. Unit-tested in `web_client/js/tests/`.

### Portfolios = Brokers (`portf_server/routers/portfolios.py`)
A portfolio doubles as a broker/account. `GET /api/v1/portfolios/` returns `website`, `description` (from `KNOWN_BROKERS` if not stored), `first/last_transaction_date`, `first/last_booking_date`, `first/last_spending_date`, and `account_type` (`'brokerage'`/`'bank'`, default `'brokerage'`). Portfolio queries alias `e.website AS entity_website` to avoid colliding with `p.website`. `DELETE /api/v1/portfolios/{id}/transactions?include_bookings=true`.

`POST /api/v1/portfolios/` accepts `account_type: Literal["brokerage", "bank"] = "brokerage"` — pass `"bank"` to create a Spending-tracking account (see Spending Tracking section). `account_type` is **create-only, immutable after creation** — verified across three independent layers: `PortfolioUpdate` (the PUT schema) omits the field entirely, `database.py`'s `update_portfolio()` whitelist excludes it, and the frontend's portfolio-edit form (`pfm_features.js`) only includes `account_type` in the request payload when `!id` (creating), never on an edit submit.

**Brokers page bank balances**: bank-type rows never have investment values (`GET /api/v1/portfolios/values` sources only `transactions`, which bank accounts never populate), so `loadPortfoliosPage()` (`pfm_pages.js`) fetches `GET /api/v1/networth/` alongside the values call and merges its `bank_accounts` list (keyed by `portfolio_id`) into the same "Value (EUR)" column instead — same derived-balance source as the Net Worth page's "Bank Accounts" card, not a separate computation. Shows the balance + "As of {date}" when a balance-bearing import exists, else "No balance imported" (muted). P&L stays "—" for bank rows (no P&L concept). Both fetches are best-effort (wrapped in try/catch) so a slow/failing values or net-worth call doesn't block the broker list from rendering. The Activity column also branches on `account_type`: bank rows show `first/last_spending_date` (imported bank-statement rows) instead of `first/last_transaction_date`/`first/last_booking_date`, since a bank account never populates those two tables — before this it silently showed "—" for every bank account regardless of import history, identical to a never-imported one.

**`cash_eur`/`cost_eur` use transaction-date FX, not today's rate.** `GET /api/v1/portfolios/values` computes `cash_eur` (deposits/withdrawals/buys/sells/dividends/interest, all FX-converted) and `cost_eur` (chronological buy/sell/split cost basis, via `compute_positions`) per portfolio. Both now convert each row at **its own transaction/booking date's FX rate** via `_get_fx_rate_on(database, currency, on_date)` — a local sibling of `_get_fx_rate` (not imported from `analytics.py`'s equivalent `_fx_on`, to avoid a circular import, since `analytics.py` already imports `_get_fx_rate` from this module) that memoizes non-stale historical rates per `(currency, date)` for the worker's lifetime. Previously both used the live current rate (`_get_fx_rate`) for every historical row regardless of date — cash_eur/cost_eur would silently re-price a year+ of foreign-currency trades at whatever the live rate happened to be on each request, drifting between page loads as the live rate ticked and diverging from what the broker's own EUR-denominated statement shows. `value_eur` (current holdings value) intentionally still uses the live rate — that's a genuine "what's it worth right now" figure, not a cost-basis one. `cost_eur` is computed by re-running `compute_positions` on a second, EUR-pre-converted copy of the transaction list (same chronological buy/sell/split math, just fed already-converted amounts) rather than multiplying the native-currency aggregate cost by a single rate at the end — the latter can't reflect that different lots of the same asset were bought at different historical FX rates. `cash_eur`'s buy/sell/dividend bucket now also includes `interest`-type transactions (previously omitted, so any `interest` transaction — e.g. from a matured fixed deposit — silently didn't move the displayed cash balance).

**Expect a small residual gap vs. the broker's own EUR figure — don't chase it to zero.** Reconciling a real MyInvestor portfolio's `cash_eur` against its full CSV statement (2026-08-18) closed most of a multi-thousand-euro gap through real fixes (see git history around that date: currency mislabeling, sign-flipped bookings, a missing deposit-maturity link, missing transactions, a duplicate-detection bug), but the last ~1–2% of a multi-currency portfolio's cash/cost figures will not match the broker exactly, for reasons that are inherent, not bugs:
- `_get_fx_rate_on` reconstructs historical FX from **daily closes** (`get_fx_eur_on`, one yfinance history call per currency-year); the broker converted each trade at its own **intraday execution-time** rate. Spot-checks on real USD trades showed ~1% per-trade drift from this alone — small individually, but it compounds across dozens of foreign-currency (USD/GBP/SEK/DKK/...) trades in a year+ of history.
- Brokers occasionally export the same line twice (see `myinvestor_csv_parser.py`'s handling of MyInvestor's own duplicate `Liq. intereses` lines) or report a correction/reversal (`ANUL. ...`) that no parser recognizes as a paired event — a rounding-scale, not gap-scale, effect.
If a reconciliation like this comes up again: match every statement line to a transaction/booking by date+amount with a tolerance that scales with trade size (a flat cent-level tolerance will flood you with FX-noise false positives), and budget the remainder as expected error rather than treating 100%-match as the bar.

### Watchlist / Goals / Sync APIs
- Watchlist: `GET|POST /api/v1/watchlist/`, `DELETE /api/v1/watchlist/{symbol}`, `GET /api/v1/watchlist/alerts/check`
- Goals: `GET|POST /api/v1/goals/`, `GET /api/v1/goals/summary`, `PUT|DELETE /api/v1/goals/{id}`. All figures come from `portf_manager/services/goals.py` (`goal_progress`, `list_goals_with_progress`, `goals_summary`), shared with the `get_goals` chat tool and `check_goals_off_track`, so every surface agrees. Per goal: `progress_pct`, `months_left`, `projected_value_eur` (today's net worth plus the planned monthly contribution at the assumed return), `on_track`, `shortfall_eur`, `required_monthly_eur` (from now; `0` when the current amount alone grows past the target, `null` when no months are left), `status` (`achieved` when net worth ≥ target, else `overdue` when the date has passed, else `on_track`/`off_track` from the projection), and the follow-up block since schema v36: `start_date` (the `created_at` date), `start_networth_eur` (baseline; `POST` stores today's net worth unless the body sets one), `months_elapsed`, `gained_since_start_eur`, `gap_closed_pct` (clamped 0–100), `actual_monthly_eur` (gain per month, `null` under one month) and `pace` (`ahead`/`behind` against `required_monthly_eur`). All pace fields are `null` for a goal without a baseline (created before v36) — nothing is guessed. `notes` is free text. `PUT` takes the same body; a missing/`null` `start_networth_eur` or `notes` leaves the stored value alone (so the original five-field client can't wipe them), `""` clears the notes, a number resets the baseline. `/summary` returns `{summary: {total, achieved, on_track, off_track, overdue, planned_monthly_eur (open goals only), next_target_date}, goals: [...]}` — one call for the page strip and the dashboard card. Current net worth basis = `networth.net_worth_eur(db)` (same total as the Net Worth page). No backend "monthly_contribution defaults from cashflow" logic — that autofill and the per-goal net-worth breakdown panel are client-side only (`pfm_features.js`, reusing `GET /api/v1/networth/cashflow` and `GET /api/v1/networth/`).
- Goals UI (`pfm_features.js`, Goals section): a summary strip (`goalsSummaryChips`: counts per status, the planned contributions of open goals — amber when above the net monthly cash flow, since several goals can't each assume all of it — and the next due date), then one card per goal with a status badge (`goalStatusMeta`), the notes, the progress bar, "Time left" as years and months (`formatMonthsLeft`), a "Since set / Pace" block (`goalPaceModel`: gain since the baseline, share of the gap closed, actual vs planned vs needed €/month, the planned amount also as a share of the net monthly cash flow via `goalPlannedShareText`; a goal without a baseline gets a hint to set one in Edit), and a status note (off track: needed €/month and shortfall; overdue: date passed; achieved). The robot button opens AI Chat with a thread named after the goal and an opening message built by `goalChatMessage` (the goal's numbers plus a prompt to judge whether it is realistic against income, monthly costs and mortgage, telling the model to call `get_household_finances` and `get_goals` first) through the shared `openChatWithContext`. The Add form has a notes field; the Edit modal adds "Net worth when set" (empty = keep) and notes. Dashboard: `loadDashboardGoals` renders `#dashGoalsCard` (one line per goal: status, thin bar, current/target, time left, needed vs planned vs actual €/month; retirement goals link to readiness instead) from `GET /goals/summary`, hidden when there are no goals. Pure helpers are tested in `web_client/js/tests/goals.test.mjs`. Design: net worth includes market moves, so the pace is "how my net worth moved", not "what I deposited" — the help text says so; a bad month is not a missed contribution.
- Sync: `GET|PUT /api/v1/sync/pdt-config`, `POST pdt-pull`, `POST pdt-push`, `POST pdt-backup`, `GET pdt-download?fmt=xlsx|ods|pdf` (Drive export of the sheet). Resolution order for `spreadsheet_id`: query param → DB `app_settings` → `GOOGLE_SPREADSHEET_ID` env var.

### Balance sheet (`portf_manager/services/balance_sheet.py`, schema v35)
`GET /api/v1/networth/balance-sheet` returns every asset and liability as a sourced, dated line: `{as_of, totals, groups}`. `build_balance_sheet(db, today=None, fx=None, fx_on=None)` is the one builder behind `net_worth_eur(db)`, the emergency-fund metric, Action Items and the retirement projection, so they cannot disagree.

- **Groups**, in order: `cash`, `deposits`, `investments`, `property`, `other_assets`, `liabilities`, each `{key, label, total_eur, lines}`. Manual categories `cash`/`current_account`/`savings_account` go to `cash`, `property` to `property`, `pension`/`investment_external` to `investments`, anything else to `other_assets`; every `is_liability` line goes to `liabilities` whatever its category.
- **Totals:** `assets_eur`, `liabilities_eur`, `net_worth_eur`, `financial_assets_eur` (cash + deposits + investments, the pot the retirement projection draws on; property and other assets are never in it), `liquid_eur` (cash plus deposits maturing within 365 days, used by the emergency-fund metric) and `stale_lines`.
- **Line:** `id`, `label`, `group`, `amount_eur`, `amount`, `currency`, `source`, `as_of`, `age_days`, `max_age_days`, `stale`, `note`, `edit` (`{kind, id}` for the UI's edit control) and `in_total`. A line with `in_total: false` is shown but adds nothing to a group total, the totals or the pot.

| Line (id) | Source | `as_of` | Max age (days) | Notes |
|---|---|---|---|---|
| Brokerage positions (`positions:{portfolio_id}`) | `positions`: `compute_positions` × latest stored price × live FX | oldest `price_date` among held auto-priced assets | 4 (`MAX_AGE_POSITIONS`) | An unpriced or undated asset makes the line stale; note "N assets unpriced". Manually priced assets are not aged; a portfolio with only those never goes stale. |
| Broker cash (`cash:{portfolio_id}`) | `cash_ledger` (`services/cash_ledger.py`, the `cash_eur` rule of `GET /portfolios/values` at transaction-date FX) | newest booking or transaction | 60 (`MAX_AGE_BROKER_CASH`) | Shown only when non-zero. **Excludes buys/sells of `asset_type='cash'` assets**, which are already a position; their interest and dividends still count (MyInvestor's `MYINVESTOR-CASH` interest). Dividends and interest count net of `tax` (withholding). A negative ledger is shown but not counted (`in_total: false`), stale, note "ledger cash is negative: deposits missing?". |
| Account valuation (`valuation:{portfolio_id}`) | `account_valuation` (see below) | row `as_of` | 7 (`MAX_AGE_VALUATION`) | While fresh (≤ 7 days) it **replaces** that portfolio's positions and cash lines. A non-empty `last_error` is shown in the note. |
| Bank account (`bank:{portfolio_id}`) | `bank_statement`: latest `spending_transactions.balance` | that row's date | 45 (`MAX_AGE_BANK`) | An account with no balance row has `amount_eur: null`, `in_total: false`, stale, note "no statement with a balance". |
| Fixed deposit (`deposit:{id}`) | `fixed_deposit`: active deposit principal | `start_date` | never stale | Past `maturity_date` and still active: note "past maturity, mark matured". |
| Loan (`loan:{id}`) | `loan_schedule` | today | never stale | Note: monthly payment and end date; "rate last confirmed <date>" when `rate_as_of` is over 400 days old (`LOAN_RATE_STALE_DAYS`). A loan with no balance left is omitted. |
| Manual line (`manual:{id}`) | `manual` | `manual_assets.as_of`, else `updated_at` | `property` 365, `cash`/`savings_account`/`current_account` 90, anything else 180 | Existing rows got `as_of = updated_at` on migration. A line whose name matches a portfolio name (case-insensitive) gets note "a portfolio with this name exists; is this line still needed?" (flagged, never fixed). |

Manual `POST|PUT /api/v1/networth/` accept an optional `as_of` date. With no valuation, a portfolio whose account valuation is stale or never fetched keeps its positions line and the note says "valued at fund NAVs, account valuation N days old" or "never fetched".

**`GET /api/v1/networth/`** keeps its response shape for the existing page and the MCP `networth` tool, and its component fields add up to `net_worth_eur` to the cent: `brokerage_eur + bank_accounts_eur + broker_cash_eur + manual_assets_eur + deposits_eur − manual_liabilities_eur − loans_eur` (`broker_cash_eur` is the counted ledger-cash lines, `loans_eur` the loan balances). A stale or never-fetched account valuation on a portfolio with no positions stays on the sheet as a stale line (never-fetched with value 0 is shown but not counted).

### Loans (`portf_manager/services/loans.py`, table `loans`)
Endpoints under `/api/v1/networth/loans`: `GET` (each row also carries today's `balance_eur`, `monthly_payment_eur` and `end_date`), `POST`, `PUT /{id}`, `DELETE /{id}`, `GET /{id}/schedule` (one row per calendar year: `year`, `balance_end_eur`, `interest_paid_eur`, `payments_eur`).

A standard annuity (French amortisation), simulated month by month with every figure rounded to cents; the final payment clears any residual. `extra_payment_eur` is a fixed monthly overpayment that shortens the term. Functions: `balance_on(loan, day)` (the principal before the start date, 0 after the last payment), `payment_of(loan)` (regular payment plus the extra), `end_date(loan)`, `schedule(loan)`, `payments_in_year(loan, year)`.

**Rate changes:** edit `annual_rate_pct` and set both `rate_as_of` and `balance_as_of` (the balance the lender reports on that date). The schedule then restarts from that anchor: the recorded balance, the new rate and the months left in the original term. Without both fields it runs from `principal` and `start_date`. Clearing a nullable field with an explicit `null` writes NULL (`update_loan`).

### Account valuations (Indexa) (`portf_manager/services/indexa.py`, table `account_valuations`)
One row per brokerage portfolio, shaped for more than one provider (`provider` is `indexa` today). `value` **includes** `cash`; the investments are `value − cash`, and the retirement projection uses that split.

- Setting `PORTF_INDEXA_TOKEN` (`.env.local`, never the database; settings key `indexa_token`) enables the client. `refresh_account_valuations(db, token, today=None, only_portfolio=None)` calls `GET /accounts/{account_ref}/portfolio` on `https://api.indexacapital.com` with an `X-AUTH-TOKEN` header; without a token it does nothing. The portfolio's `total_amount`, `cash_amount` and date become `value`, `cash` and `as_of` (today when the API gives no date). A failure writes `last_error` and **keeps the old value and `as_of`**, so the line simply goes stale after 7 days.
- `price_updater.run_price_update` runs it after the price pass; the run result carries `valuations_refreshed` and `valuation_errors`.
- Endpoints (`/api/v1/networth/`): `GET /valuations`; `POST /valuations {portfolio_id, provider, account_ref}` links a brokerage portfolio (422 for a bank portfolio, 404 for an unknown one), keeps an existing row's good value, and refreshes once when the token is set and the provider is `indexa` (the response carries `refreshed`); `POST /valuations/refresh` refreshes all by hand; `DELETE /valuations/{portfolio_id}` unlinks. A new link starts with `value 0` and `as_of 1970-01-01`, which the sheet treats as "never fetched".
- The MyInvestor and Coinbase portfolios keep their positions-based lines.

### Retirement readiness (`portf_manager/services/retirement.py`, `portf_server/routers/retirement.py`)
Answers one question: if the household keeps living at today's financial level, does the money last from the day work stops until `horizon_age`? Everything is in **today's euros** and **before tax**. The router is mounted at `/api/v1/retirement`.

**Endpoints:** `GET|PUT /plan` (partial update; unknown keys are ignored, `null` clears only the two dates, ages must satisfy `0 < retirement_age ≤ statutory_age < horizon_age ≤ 120`, `withdrawal_tax_pct` in `[0, 100)`), `GET|POST /incomes`, `PUT|DELETE /incomes/{id}`, `GET /readiness`. Incomes: `name`, `owner` (`self` or `partner`), `monthly_eur` (gross, today's euros), `from_age`, optional `to_age` (greater than `from_age`; none = for life), `indexed`, `source`, `as_of`, `notes`.

**Plan** (one JSON `app_settings` key, `retirement_plan`), with defaults: `retirement_age 65`, `statutory_age 67`, `horizon_age 95`, `real_return_pct 3.0`, `pessimistic_real_return_pct 1.0`, `cash_real_return_pct -2.0`, `withdrawal_tax_pct 0.0`, `spending_months 12`, `spending_includes_loan_payments true`, `excluded_categories ["Income Tax", "Social Security", "Invest", "House purchase"]`, `birth_date null`, `partner_birth_date null`. Ages are **calendar ages** (year minus birth year), so retirement, a pension start and the end of saving land in the calendar year of the birthday. The household is projected as one unit with constant spending to `horizon_age`.

**Inputs**
- *Pot:* the balance sheet's `financial_assets_eur`, split into investments (positions, and valuations minus their cash), cash (the cash group plus valuation cash) and deposits, which earn their own rate minus `ASSUMED_INFLATION_PCT` (2) until the maturity year and then become cash. Lines with `in_total: false` are left out. The loan balance never reduces the pot: the loan is paid out of spending.
- *Spending target:* the average monthly outflow over the last `spending_months` complete months that have bank imports (the window rule of `savings_and_buffer`; the month in progress and months with nothing imported never count), non-transfer rows only, **minus** `excluded_categories` expanded to their descendants in the category tree (`expand_categories`). The response carries `spending_breakdown` (category to monthly euros) and `spending_excluded`.
- *Savings now:* income minus spending, excluding only `Invest` and `House purchase` (taxes are real outflows today), over the same months, as a yearly figure floored at zero and continued until retirement.
- *Loans:* each loan's `schedule()`. With `spending_includes_loan_payments` (default, because the mortgage debit is a spending row) the scheduled payments are subtracted from the need in the years after a loan has ended; with `false` they are added while it runs.
- *Pensions:* `retirement_incomes`; a partner income needs `partner_birth_date` or it is ignored with a warning. An income applies from `from_age` (inclusive) to `to_age` (exclusive); `indexed = false` loses `ASSUMED_INFLATION_PCT` a year in real terms.

**Projection** (`project`), year by year from the current calendar year to `horizon_age`, for each retirement age (`retirement_age`, `statutory_age`) and each return case (base, pessimistic). The first year is pro-rated by the months left. Deposits mature into cash at the start of their maturity year; investments grow at the case's real return and cash at `cash_real_return_pct`. Before retirement the yearly savings go into investments. From retirement the need is `target × 12 − pensions` (adjusted for loans as above, floored at zero), grossed up by `1 / (1 − withdrawal_tax_pct/100)`, and drawn from cash down to `CASH_RESERVE_MONTHS` (6) of spending first, then investments, then the rest of the cash, then deposits. When the pot cannot cover a withdrawal it is emptied and the age is recorded as the depletion age.

**Verdict** (base case): `on_track` when the pot is not depleted before `horizon_age`; `short` when it is depleted strictly after `retirement_age + 10`; `at_risk` otherwise. `sustainable_monthly` and `extra_saving_needed_monthly` are found by bisection (tolerance 1 euro, 60 iterations) on the same simulation, each with its own scenario's return case. `extra_saving_needed_monthly` is 0 when already on track, and **None when no saving year is left or when even the cap (100,000 a month) does not make the pot last**.

**`GET /readiness` response:** `status` (`ok`, `needs_setup` when there is no birth date, `insufficient_data` when fewer than 6 complete imported months exist; both carry a `reason`), `as_of`, `plan`, `scenarios` (four: each `retirement_age` × `base`/`pessimistic`, with `verdict`, `lasts_until_age`, `pot_at_retirement_eur`, `pot_at_horizon_eur`, `sustainable_monthly_eur`, `gap_monthly_eur` (target minus sustainable; negative is a surplus), `extra_saving_needed_monthly_eur` and `path`, one row per year with `age`, `year`, `investments_eur`, `cash_eur`, `loans_eur`, `pensions_eur`, `withdrawal_eur`), `inputs` (`age`, `financial_assets_eur`, `investments_eur`, `cash_eur`, `spending_target_monthly_eur`, `spending_breakdown`, `spending_excluded`, `spending_months_used`, `spending_includes_loan_payments`, `savings_now_yearly_eur`, `income_monthly_eur`, `loans`, `incomes`, `stale_lines`) and `warnings` (no pension entered, stale lines counted at their stale value, partner income ignored, the loan-payment assumption, and "before tax" while the withdrawal tax is 0). The MCP tool `retirement_readiness` (read-only) prints the verdicts, lasts-until ages, gap and warnings for both ages.

**UI wiring** (`web_client/js/pfm_analytics.js`): `loadNetworthPage` renders the balance sheet (`renderBalanceSheetRows`, `renderBalanceSheetTotals`), the retirement card (`loadRetirementCard` → `retirementVerdictHtml`, chart series from `retirementChartSeries`, plan form behind the gear icon, incomes list with quick-add suggestions), and the manage section (manual lines with an "as of" date, loans, valuations). Goals: a goal whose name contains "retire" shows `retirementGoalLineHtml` ("Readiness: …", linking to Net Worth) instead of a progress bar (`pfm_features.js`). Help entries: `nw_*` and `rt_*` in `help_text.js`. Action Items: see that doc. The Wealth Simulator's "Load from Net Worth" takes the mortgage balance, rate and payment from the first loan when one exists (`forecastPrefillFromLoan`).

**After deployment, the owner does by hand** (none of it is in the repository): add the mortgage as a loan and delete the typed liability line; set `PORTF_INDEXA_TOKEN` (read at startup, so restart the backend afterwards) and link the Indexa portfolio to its account reference; decide per brokerage portfolio whether to keep ledger cash or a synthetic cash asset (never both); enter the birth date, the expected state pension and, if wanted, the partner's details in the plan; give the home line an "as of" date; and remove typed manual lines that now duplicate a portfolio.

**Known limits**
- A stale valuation on a portfolio with no positions is shown at its stored value (stale, counted); if that portfolio also has non-zero ledger cash, the cash is counted twice, because the valuation value already includes it.
- `GET /networth/` components sum to `net_worth_eur` through `broker_cash_eur` and `loans_eur` (see above).
- A loan that starts mid-year subtracts the pre-start months of its first payment year from the need.
- The retirement chart does not redraw on window resize.
- Returns are deterministic real rates, not a Monte Carlo; a bad sequence of early returns is not modelled.
