**Recent (v2.5.53):** **Budget: separate money you kept from money you spent.** The first real budget read a monthly "spending" figure of which roughly a third wasn't consumption — a mortgage repayment, unmatched transfers, a renovation, and contributions to a pension/brokers. Three changes, all confined to the budget layer so the Spending page's own totals and the Budget↔Spending reconciliation are untouched. (1) **An investment line can be keyed by a spending category**, not just a broker: `is_broker_ref(ref_key)` (`str(ref_key).isdigit()`) tells the two apart — all digits means a broker measured from Deposit `bookings`, anything else a Spend-rooted category measured from its bank outflows. The bank side is the only way to budget a destination pfm doesn't track (a pension plan) and the only one that can be reclassified; it joins the same Spend coverage set via the new `line_uses_category` predicate, so its euros can't also surface as unbudgeted spending. (2) **`line_type` is editable in place** — a dropdown per row in the Edit tab and per proposal in the seed-review panel, since reclassifying is the main thing anyone does to a seeded budget. `ref_key` stays immutable so coverage can't be sidestepped, and validation re-runs excluding the line's own key so it can't conflict with itself. Seeding deliberately **doesn't guess** types (whether an outflow is debt, a contribution, or consumption is a judgement about intent, not a pattern in the data), so it defaults to `spending` and makes the choice one click at review time, with an inline explanation that only Spending counts toward the spending total. (3) **Root-dominant seeding**: walking only a root's children missed income filed against the bare `Income` root — nearly all of it on a real account, proposing an amount an order of magnitude below the real one. Seeding now compares a root's own direct activity against the sum of its children's and proposes whichever holds more (they can't coexist, since a root line covers the whole subtree), using the whole-subtree total as the amount because that's what the line measures. Plus one invariant that fell out of testing: **a section reports one measurement basis, never the sum of two** — with a bank-side investment line present, `bank_basis` empties the Investments section's broker-side `unbudgeted` list and sets `unbudgeted_suppressed` (the Overview explains it in a footer row), because a bank outflow to a broker and that broker's Deposit are the same euros and the broker figure is inflated further by moves between the user's own accounts. Also fixed while testing: `_line_label` assumed every investment line was broker-keyed and 500'd on a category-keyed one. Backend HUP + web rebuild; 1107 unit tests and 100 JS tests pass.

**Recent (v2.5.52):** **Budgeting — named monthly plans with budget-vs-actual variance (db v29).** pfm already held every input a budget needs (categorized bank spending, the Income/Spend category tree, broker deposits, liabilities) but had no concept of *intent* — the only "planned" figures were the five coarse `monthly_cashflow` rows on the Net Worth page, with nothing computing a variance against them. New `budgets` + `budget_lines` tables (schema v29), `portf_manager/services/budget.py`, `portf_server/routers/budgets.py`, a top-level **Budget** page under the Planning nav section (Overview / Edit / Scenarios tabs), a Dashboard card, and a `check_budget_overruns` Action Items check. A budget is **open-ended** — one €/month per line applying to any month you look at, plus per-month overrides for lumpy costs (insurance in March, holidays in August) — and several coexist as user-defined scenarios (base / best case / worst case) with exactly one flagged active. Lines address four things: spending categories, income categories, per-broker investment contributions (matched against net `bookings`, so a bank→broker transfer isn't counted twice), and debt payments. **"Seed from actuals"** proposes a line per top-level category from the last 12 complete months and writes nothing until applied, so the first budget is a review-and-adjust job rather than 25 empty fields — against real data it proposed 29 lines in one call. Three rules make the numbers trustworthy: `variance_eur` is signed so **positive always means favourable** (under plan on a cost, over plan on income or a contribution, with an explicit `favourable` flag so no client re-derives the direction); a budget can't hold two category lines on the same branch, since a parent's actual already sums its children's subtree (400 via `coverage_conflict`, and the bulk-save path had to check the rest of the batch, not just stored lines, or two overlapping lines arriving together both slipped through); and **unbudgeted actuals get their own rows counted in the actual totals**, so "under budget" can't be an artifact of leaving half your spending out of the plan. That last one exposed the one real bug of the build: attributing unbudgeted actuals by the category's *tree root* silently dropped a refund in a Spend category, a charge in an Income category, and anything unfiled — including `uncategorized`, which exists in a real database as a parentless `is_root=0` node with no root at all — leaving the spending totals materially short of `GET /api/v1/spending/trend`. Attributing by **sign** instead (what `/spending/summary` and `/spending/trend` already do) made the two surfaces reconcile to the cent across all six months, now the regression-tested invariant. Also: `subtree_names` was extracted from `/spending/categories/breakdown` into the shared service rather than duplicated, and `make test-js` was fixed (Node 24 no longer expands a bare directory passed to `--test`, failing with a misleading `MODULE_NOT_FOUND` — the target now names `*.test.mjs` explicitly). DB version bump (`docker compose restart portf_backend_dev`) + web rebuild. Two UI honesty fixes came out of the browser pass: a month with no imported statement reads as zero spend (i.e. gloriously under budget), so `budgetMonthsWithoutActivity` now names those months as a banner on the Overview tab and makes the Dashboard card suppress its variance figure rather than show a flattering green number; and the trend chart was narrowed to spending + debt, since including broker deposits (an order of magnitude larger and lumpier) buried the very comparison it exists to make. 1095 unit tests and 100 JS tests pass. Design: `docs/superpowers/specs/2026-09-03-budgeting-design.md`.

- Routers: auth, assets, transactions, portfolios, entities, sectors, LLM, tax
- Docker support with docker-compose

- Bootstrap 5 + Chart.js, Vanilla JS, no build step

- PDT / Google Sheets sync, platform export (Yahoo Finance, Simply Wall St)

### Database — ✅ Working
- SQLite (default) + PostgreSQL support via database factory

- Tables: assets, transactions, portfolios, prices, bookings, dividends, watchlist, goals, research_notes, price_targets, networth snapshots, fixed_deposits, monthly_cashflow, app_settings, kv_cache, push_subscriptions, chat_sessions, price_update_runs, and more

### LLM Integration — ✅ Working
- Provider-agnostic abstraction (`llm_client.py`)
- **Default: auto-detect** — tries Ollama locally first (zero config), falls back to Gemini, then OpenRouter, then Anthropic

- Config via `PORTF_LLM_PROVIDER` (`auto`/`ollama`/`gemini`/`openrouter`/`anthropic`) + `PORTF_LLM_MODEL` + `ANTHROPIC_API_KEY`
- Search-grounded research: Gemini/Anthropic implement `generate_with_search()`; research endpoint uses it when available, falls back to yfinance headlines
- Three use cases: transaction extraction, stock reports, chat/advisor
